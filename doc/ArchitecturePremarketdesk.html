doc / architecture

PremarketDesk

There is no server, no queue, and no service. PremarketDesk is seven Windows Task Scheduler job scripts on one machine, registered as nine tasks: the nightly runs twice (22:15, and again at 07:00 as nightly-catchup) and the watchdog runs twice (07:25, repeating every 30 minutes for two hours, and once at 22:45). Five of the scripts wake on their clock time, read the files the earlier jobs left behind, and leave files for the next. The sixth is the watchdog, which reads the others' dated logs and Task Scheduler's own record, then relaunches the .bat of whatever is safe to rerun. The seventh is the quota meter sampler, which is not a step at all: it takes one reading of the shared vendor counter every thirty minutes of every day, weekends included, because the job trail can say which step spent what and cannot say when, and the overnight silence between 22:45 and 07:00 is exactly where a sibling project draining the shared key would hide. The schedule is the architecture.

01  Purpose

What this is for

PremarketDesk has two goals that live on different timescales, and most of the confusion about it comes from reading one and expecting the other.

The daily goal is orientation before the bell. Between 08:46 and 08:49 an email arrives naming the stocks that gapped overnight, the headline behind each one, whether the premarket volume behind the move is unusual for that ticker or ordinary, and where price sits against the prior high, the premarket high, and the 200-day average. It replaces the hour most people spend scanning between 07:00 and 09:30. It is not a signal and cannot be one, because gap setups resolve in the first fifteen minutes and the report is read at 09:00.

The long goal is finding out whether the screen is worth anything. Every morning the system writes down what it claimed and where the levels were. Every night it writes down what actually happened. After enough sessions that record answers questions that cannot be answered today: whether gap plus catalyst plus premarket relative volume has an edge on this data rather than on the data of whoever published the thresholds, whether a high confluence score outperforms a low one, and which component of the score is carrying the result. Until then the thresholds in CRITERIA.md are seed values copied from a third party and the report is a well-formatted list of names that met a stranger's rules.

The briefing exists to keep the system in daily use long enough for the record to become worth reading. That is the whole design in one sentence.

Sample unit is the session, not the row. Twelve candidates from one morning share a market, a macro print, and often a sector move, so they are not twelve independent observations. Any analysis of the record aggregates to one figure per session before comparing conviction buckets.

02  Timeline

The weekday, end to end

Each job wakes on its clock time, does one thing, and exits. No job in the data path calls another. What passes between them is files on disk, which is why a dead job shows up downstream as a missing file with a stated reason rather than as a crash.

The one exception is the watchdog (tasks/job_monitor.bat, registered as monitor, which runs every 30 minutes for two hours from 07:25, and as monitor-night at 22:45). It reads Task Scheduler's own record for each job alongside that job's dated log, and relaunches the job's .bat when the job fired and died, when it never fired at all because the machine was asleep, when no collector is alive inside the collector window, or when universe.json has gone past universe_rerun_after_days = 8. Only idempotent work is rerun, at most max_reruns_per_job_per_day = 1 per job per day so a hard failure cannot loop, and never a second collector while one is still writing bars, because two collectors folding the same tape write duplicate minutes and double the premarket volume downstream.

04  Morning flow

The morning relay

Each stage writes one artifact and the next stage reads it. Nothing talks to anything else at runtime. If a stage dies, its file is simply absent and the next stage records the absence in the packet's gaps_to_fill list rather than raising.

05  Opened up

Inside the scan

The scan does more work than anything else in the system and it is the only place where a decision is made. Eight ordered steps, no model involved in any of them, and between the seventh step and the eighth an assertion that can end the run outright. After every price and prior close is attached and before any eligibility flag or score is computed, vintage.py checks five things: that every priced candidate's price_time is dated today and falls inside the 04:00 to 09:30 premarket window, that no prior_high sits below its own prior_close (two fields read from one OHLC bar cannot do that), that the prior close is dated to the prior trading session per the exchange calendar rather than merely to some earlier date, and that every market snapshot row is either dated today or labelled prior_session_only and dated to that session, and that every notable movers row is stamped with the session its own leg declares. That last check asks a different question from the other four, because that section mixes a premarket leg with completed session legs on purpose. It walked NO rows at all until 2026-08-20, and not because the section was unbuilt: vintage.enforce is called on a hand built dict carrying candidates, market snapshot and session date, so the key it looks for was never in what it was given. Layer 4 shipped on 2026-08-20 and passing notable_movers into that dict is what armed the check. The same day it was given something to read: both universe legs are stamped with the closes sidecar's sessions.c1, which is the calendar's answer, and check (e) validated that stamp by asking the calendar again, so no packet the scan built could fail it. The sidecar now records the session date the VENDOR stamped on the rows it sent, and the section refuses to publish a leg the vendor contradicts. A violation rewrites data/UNVERIFIED naming each failing row and the check that caught it, and the scan exits non-zero, so nothing is stamped, no packet is written, and the morning chain stops before the analyst call. There is deliberately no degrade path: a stale price is not thin evidence a report can hedge around, it is a wrong number wearing the costume of a right one.

Step 2 gained a fill warning on 2026-08-29, and it is a warning and never an approval. A third of what the report publishes has a headline level no market stands behind, and until then the reader found that out three weeks later in a database. Alpaca refuses a running session, so the morning cannot run the real check; it computes its own band from the collector's sample instead and prints it in Skips and traps. Measured over 66 rows, thin caught 6 of the 10 the night calls untradeable and flagged 6 of the 44 that were fine, and not flagged got 4 untradeable levels past it, which is why its silence means nothing. It cannot be calibrated better, and the reason is structural: the morning centres its band on pm_high and the night on entry_ref_true, which differ by a median 1.19 percent and by up to 20.9, so on the names that matter most the two bands do not overlap. A floor sweep from 5,000 to 100,000 dollars trades one error for the other at every step. So it keeps its own vocabulary, thin and not flagged, never the night's plausible, which a reader at 08:45 would take for a verdict that cannot exist until the session is over, and it reads its band width from [Truth] rather than restating it so the two cannot drift apart.

And the packet gained the ledger's counts. The scan calls C60's record_so_far and carries the result into C29. It is the first thing in the morning path that reads the record back rather than only writing to it, it costs one local table read and no vendor call, and what it produces is a report section that is not about today's names. See section 08.

Inside the analyst pass

This is the boundary the whole design is built around. Everything to the left of it is deterministic and reproducible. Everything to the right is prose. The model never chooses a name, never sets a number, and never changes a conviction.

07  Coverage

The blind window and the night

Two facts force the night pipeline to exist. The premarket session opens at 04:00 but the collector only starts listening at 07:20, so the morning's premarket high honestly describes a partial window. And the vendor publishes its one-minute intraday bars several hours behind live, so the full truth does not exist anywhere until the evening.

Since 2026-08-29 a second vendor measures the same window, and it is named rather than hidden. C59 fetches the identical 04:00 to 09:30 stretch from Alpaca's full SIP tape and writes pm_volume_true, pm_rvol_true and pm_float_rotation_true beside the morning's estimates. It runs at night because it has to: the free plan serves the sip feed for a session that is OVER and refuses a running one with 403, measured in doc/ALPACA_PROBE.md. A column suffix is not a provenance. C20's pm_high_true comes from EODHD intraday and every column C59 writes comes from Alpaca, so truth_source carries the vendor on every row. And both sides of every ratio come from one tape: pm_rvol_true divides an Alpaca window into an Alpaca baseline over the same window on the prior sessions, because dividing an Alpaca numerator into the EODHD baseline the morning uses would repeat, one vendor down, the exact defect the pass exists to correct.

The same pass measures the reference levels, and that changed what the record says. entry_ref and stop_ref are the collector's raw live pm_high and pm_low, which are the extremes of a socket SAMPLE. A sample understates a maximum and overstates a minimum, so every excursion measured from them is biased in a known direction. C59 writes entry_ref_true and stop_ref_true off the whole tape, beside the sampled pair and never over it, and C21 fills mfe_pct_true and mae_pct_true from them in a separate arithmetic pass that makes no vendor call. Measured over 48 rows across 5 sessions, BOTH MEDIANS CHANGE SIGN: favourable +0.81 becomes -2.13 percent and adverse -1.92 becomes +0.15. The count that reached the entry reference falls from 29 of 48 to 20. The record had been reporting a median name as having reached a level it never reached. The premise that specified the work was inverted. Split into its two causes, the sampling inside the minutes the socket did hear is +0.10 percent at the median and the 04:00 to 07:20 stretch it never hears is +0.98: ten to one the other way. The socket reproduces the extremes of the minutes it hears almost exactly, and any fix belongs at [Collector] start_time rather than at the feed. Not acted on.

A level is not a price you could have got. So C59 also asks whether anything traded near entry_ref_true: total premarket volume, the volume and notional within [Truth] fill_band_pct = 0.5 percent of that level, and how many distinct minutes carried a trade there. fill_plausible is a THREE STATE field and never a boolean, plausible / implausible / unknown, because a row with no evidence is not a row that failed and no row is called plausible on absent evidence. Over 66 live rows across 7 sessions: 44 plausible, 10 implausible across 4 sessions, 12 unknown. The band volume is an UPPER BOUND and is called one everywhere: a one minute bar carries o, h, l, c and v and no distribution, so a minute running from below up into the band counts whole. Correcting that needs trade level data this plan does not buy.

A true high below the live high is suspicious, not impossible. The trades socket and the published bars can differ on odd lots, condition codes, and late corrections, so a legitimate feed difference will trip this. The backfill records the size of the discrepancy as a percentage rather than a boolean, so small feed noise stays visibly distinct from a real fault, and a human decides. Nothing is silently corrected.

What the socket costs on the vendor's counter, measured 2026-08-13. The old claim that the collector consumes no API calls was a client side observation about this process. It is now a vendor side measurement: measure_socket_cost.py read /api/user before and after collector-only runs while nothing else used the key. A 20 minute run with 10 connections, 10 full 38 symbol resubscriptions, and 9 reconnects moved the daily counter by exactly zero, and a second 20 minute run with 3 forced drops added (13 connections, 13 resubscriptions, 12 reconnects) also moved it by zero, so the per reconnect and per resubscribe cost is a measured zero, not an assumption. Reconnect and resubscription counts now land in each morning's packet next to bars_total, so a flaky morning is on the record. Scope: both runs rode the quiet evening tape; an earlier window that streamed 1,574 live trade messages straddled the counter's daily reset (20:00 ET, midnight UTC, also learned here), so the per message cost on a heavy live tape is the one number still owed. It is measurable any weekday by running measure_socket_cost.py inside the 04:00 to 07:15 window, before the scheduled jobs wake and while no other project touches the key.

What one bulk live snapshot costs, measured 2026-08-13 at 23:05 ET. measure_bulk_cost.py read /api/user, watched the meter sit still for a 45 second quiet window, made exactly one bulk live OHLCV request, and read the meter again. The counter moved by 100 for 18,341 returned symbol rows in one HTTP attempt. That reads as a flat per request rate, not a per symbol one, and the quiet watch saw zero drift from the script's own meter reads, so the whole 100 belongs to the bulk request. That was the bulk live endpoint, and the morning path no longer calls it: it serves the last completed session, so ranking by it ranked yesterday's movers. It survives only inside measure_bulk_cost.py, and test_pool.py fails if discover.py names it again. What the morning buys instead is three end of day bulk calls, all in discover at 07:15: the prior session and the one before it so the move is read close to close, and a third for the universe closes sidecar, which the report's notable movers section needs at the same vintage as the other two. The 07:15 pass moved the meter by 306 on 2026-08-20 against three bulk calls, so about 100 a call. The nightly recall pass buys two more of the same call at 22:15 and the weekly universe rebuild buys twenty, one per lookback session. At about 100 each, every one of them sits far below the 1,000 per call bulk_redesign_line in CRITERIA.md at which bulk calls would dominate the account, so the conclusion this measurement settled holds for the endpoint that replaced it. The same session recorded why the meter must be read rather than inferred: at 23:03 ET the counter already showed 49,999 used on a quota day that had opened at 20:00, none of it this project's spending.

08  Record

One picks row, four passes, one ledger row

The clearest way to see the system is to follow a single database row. The scan creates it in the morning, the backfill and the truth pass widen it the same night, and the outcomes pass returns one and five sessions later to record what the market actually did. Since 2026-08-29 a fifth pass writes to a different table entirely, and it is below the figure.

The fifth pass writes a ledger row, not a picks column. C60 applies ONE written rule from CRITERIA [Paper] to every live pick and books the result into C64, keyed on (date, ticker, rule_version). The rule was written into CRITERIA before any of the code existed, which is the only order that makes it a rule rather than a description of what the code happened to do: trigger at the first regular-session minute whose high reaches entry_ref_true, entry at max(entry_ref_true, that minute's open), stop at stop_ref_true, a minute that both triggers and stops booked as STOPPED because one bar carries no sequence, exit at the session close if the stop never came, no target deliberately because a target is a free parameter 16 trades will fit any value of, and a NULL P&L rather than a zero when the trigger never fired. Any row whose fill_plausible is not plausible is skipped WITH ITS REASON WRITTEN, never dropped.

Every rule version is booked side by side over the same trades. [Paper]'s sizing map is the version registry, so a new version lands beside what the old one produced and never over it: a ledger that overwrote itself on every rule change could not answer whether the change helped, which is most of what a ledger is for. v2 differs from v1 in exactly one thing, the position size, from a fixed 10,000 dollar notional to a fixed dollar risk. Entry, stop, exit, tie break and skip rule are v1's byte for byte, so the two book the same trades and any difference is attributable to the sizing alone. Over the first 16 trades: v1 total -3,487.81 with a worst single trade of -1,912.54, v2 total -2,713.74 with a worst of -748.90, on slightly less total risk. Every per-trade PERCENT return is identical under both, which is the point. Sizing cannot change what a trade did; it changes the portfolio's shape. [Paper] pre-registers the verdict at 200 trades across 60 sessions and 16 is not it.

And the morning reads the ledger back, which nothing did before. C16 calls C60's record_so_far and puts the counts in the packet; the report renders them in a section that is not about today's names. That section exists because last week's individual winners and losers predict nothing about this morning. What carries something is the SHAPE of what those trades did, so the ledger records minutes_to_trigger from the OPEN, minutes_to_peak from the ENTRY, and mfe_pct_held, which is what the POSITION was worth while it was open and is not picks.mfe_pct_true. Every count arrives over BOTH denominators, rows and sessions, and REPORT_TEMPLATE.md forbids the model turning any of them into an instruction or calling any of them a pattern, a signal, an edge or a tendency. Reading it costs the 08:45 window nothing: it is one local table read, and C60 imports its Alpaca client inside book() rather than at module scope so importing the ledger from the morning pulls no HTTP client into that window.

09  Stores

Data store read and write matrix

Every store has exactly one writer in the morning path, which is what makes a missing file unambiguous. The picks table is the single exception and is written by three components at three different times, always to different columns of the same row. The gate marker has two writers, verify_morning.py by hand and vintage.py from inside the scan, and one reader, deliver.py, which refuses to send while it exists. Two columns were added on 2026-08-20 for stores the page had never carried: the published archive (C54), whose single writer is build_archive at the end of both the morning chain and the nightly, and the job trail (C56), which every scheduled step appends one line to as it exits. Five stores are not columned here. The gap_stats table (C41) is written weekly by C40 and read at 07:15 by C13, so nothing in the morning path touches it. The quantifier flag log (C57) is written by the analyst's guard and judged by hand through C55. And the exchange calendar cache (C58) is read by C50 as the first step of every weekday job and rewritten only by the nightly's refresh pass. Two more joined them on 2026-08-29: the paper ledger table (C64), whose single writer is C60 at 22:15 and whose readers are C61 and, for the record block only, C16; and the weekly page (C65), written by C61 and read by nobody, which is what a reporting layer should be.

10  Failure

Failure behaviour

No job in the data path retries another and no job waits on one. The watchdog (src/ops/monitor_jobs.py, fired every 30 minutes for two hours from 07:25 and again at 22:45) is the deliberate exception: it checks Task Scheduler's record against each job's dated log and relaunches only what is idempotent, at most max_reruns_per_job_per_day = 1 rerun per job per day, so a hard failure cannot loop. The nightly is always safe to rerun, the morning chain is rerun only until rerun_chain_until = 09:30 because after the open a premarket report is history, and the collector is restarted only when no collector is alive, because two collectors folding the same tape write duplicate minutes and double the premarket volume downstream. The design question for each failure is otherwise only what is missing downstream, what the next stage does about it, and whether the email still goes.

Only one failure is unrecoverable. A scan that dies at 08:45 loses that session permanently, because premarket state is live and cannot be fetched again afterwards. 11  Rules

Load-bearing rules

Seven decisions that shape everything above. Changing any of them changes the architecture rather than the configuration.

One vendor
EODHD is the only vendor a published number comes from

REST for quotes, history, news, and calendars. The trades websocket for live premarket. Nothing in selection, collect or morning calls a second vendor, so there is never a question of which feed a number in the report came from.

This rule was narrower until 2026-08-29 and the change is worth stating plainly. It used to read "the only market data source in the pipeline", with Alpaca named as a research exception nothing in night imported. That is no longer true: C59 and C60 are scheduled night steps and both read Alpaca. What the rule protects is unchanged, because the boundary is the one that matters. Alpaca measures the RECORD, after the fact, into columns that carry truth_source and sit beside the morning's values rather than over them. It cannot reach a report, and it could not if someone wanted it to: the free plan refuses a running session with 403, so there is no version of this that runs at 08:45.

One place
Every threshold lives in CRITERIA.md

No Python file contains a screening number. The reader raises on anything missing, so a threshold cannot quietly exist in two places and drift.

The boundary
Python decides, the model narrates

Membership, eligibility, scores, and conviction are all computed before the packet is piped to the CLI. A containment check fails the run if the report names a ticker the packet does not carry.

No guessing
Missing evidence is null with a reason

A relative volume that cannot be computed honestly is null plus a reason string, never a substituted proxy. The disclaimer line names every such candidate by ticker.

No overwriting
Corrections sit beside the original

The night writes true premarket columns next to the morning's live values and never over them. The distance between them is a measurement the project needs, not an error to clean up.

One rule
The paper rule is written in CRITERIA before it is written in code

Entry, stop, exit, size and every refusal live in CRITERIA [Paper], and C60 applies them. ONE rule, not a family: no target, because a target is a free parameter that sixteen trades will fit any value of, and a rule with something to tune is a rule that cannot be wrong. Versions are booked side by side over the same trades, each differing from the last in exactly one thing, so a change that helps can be told from a change that happened. And the verdict is pre-registered at 200 trades across 60 sessions, in the same file, before the count gets there.

Human gate
No email until a real morning is verified

While data/UNVERIFIED exists, sending is refused regardless of configuration. Only a person who has checked a live morning's numbers against a reference deletes it.
